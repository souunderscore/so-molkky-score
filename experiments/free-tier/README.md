# 無料構成の事前検証

2026-10-28作成。承認済みの[仕様](../../docs/stream-management-spec.md)に対する独立した検証コードです。
**本番用の認証・同期サーバーではありません。既存のindex.html、overlay.html、Firebase Rulesは変更しません。**

## 今回確認したこと

- Node.js v24.22.1上の検証テスト16件が成功。
- 2リンクで別試合を扱い、配信対象のみ表示状態を更新できる。
- 無効化、廃棄、担当交代、古い更新番号の入力を拒否する。
- 同じ更新の再送を二重反映せず、同じIDの異なる内容は拒否する。
- 次試合を開始しても前の試合が残り、選択中リンクの表示は次試合へ追従する。
- 原子的な更新の再試行を模した競合試験で、同時担当取得・同時スコア変更が両方成功しない。
- パスワード候補PBKDF2-SHA256 / 600,000反復で正誤を照合でき、保存値に平文を含めない。
- Wrangler 4.154.0のローカルworkerdで、検証用パスワードの照合がHTTP 200 / valid:trueで成功。

## 無料枠についての結論

**無料プランでの運用可否は、まだ確定していません。**

ローカルNodeの5回測定では照合の壁時計時間約115〜161ms、プロセスCPU時間約115〜161ms。
ローカルworkerdの1回測定では壁時計時間162msでした。
これらはCloudflare本番の課金対象CPU時間とは別の数値であり、FreeのCPU上限との直接比較はできません。
特にローカルで正常に動いても、本番のFree上限内で動く証明にはなりません。

Cloudflare Free上の隔離した検証WorkerでCPU使用量とエラーを測定し、候補の適否を判断します。
CPU上限に収めるためにパスワード照合を単純なハッシュや平文照合へ弱めることはしません。
成立しない場合は、認証処理を既存の無料認証サービスに委ねるなど、構成を再検討します。
本番の課金設定を有効にすることは今回の作業に含めません。

## 実行

追加パッケージ不要、Node.js 24以降:

```sh
cd experiments/free-tier
npm test
npm run bench
```

Cloudflare互換のローカル確認に使用したCLIはWrangler 4.154.0。
一般的な環境では次のコマンドで検証Workerを起動できます。

```sh
npx wrangler@4.154.0 dev --local
```

Workerは秘密設定がない限り503を返します。検証用の秘密設定:

- PROBE_TOKEN: ランダムなテスト用トークン。
- PROBE_VERIFIER: hashPassword()で作った、合成テスト用パスワードの検証値のJSON。

実際の管理パスコードや秘密の回答を使用しないでください。
ローカルでは.gitignore対象の.dev.vars、実環境ではWorkerのSecretsに設定します。
トークンはURLへ含めず、Authorization: Bearerヘッダーで送ります。
POST /probe/password にJSONのpasswordフィールドを渡すと照合結果を返します。
レスポンスのelapsedWallMsはCPU時間ではありません。本番測定はCloudflare側のCPU指標も確認します。
検証終了後は検証Workerを停止・削除してください。

今回の実行環境ではネットワークインターフェース列挙が利用できず、ローカルCLI起動時だけ
ループバックの列挙へフォールバックさせました。アプリや配布コードにはこの環境固有の対応を含めていません。

## まだ実装していないこと

- Firebase接続、サーバー認証情報、実DBのトランザクションとRules。
- 管理画面、管理セッション、パスコード変更・秘密の質問による復旧、誤入力制限。
- 入力リンクの秘密トークン検証、公開表示データの抽出、入力スキーマと得点整合性の検証。
- 交代申請・承認の通信プロトコル、権限の永続化。
- 端末内の永続的な未送信キュー、再読み込み復旧、未反映データの確認画面。
- 本番FreeのCPU・実通信量の測定、10試合同時進行の負荷試験。

sync-model.mjsの管理操作は、呼び出し元で管理認証される前提です。
モデルをそのままHTTPで公開しないでください。入力担当のsessionも、サーバーが発行する
推測困難な秘密を意味し、端末が名乗るIDを信用する設計ではありません。
更新のチェックと保存は必ず1つの原子的な処理にしてください。
競合テストはメモリ内のcompare-and-setモデルであり、実Firebase側の競合試験ではありません。
